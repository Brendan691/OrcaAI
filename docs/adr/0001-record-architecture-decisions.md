# 1. 用 ADR 记录架构决策

- 状态:已接受
- 日期:2026-07-27

## 背景

项目此前"文档说的"和"代码做的"对不上:README 讲四件套,compose 里却有七个服务;`AGENTS.md` 引用的 `CONTEXT.md` / `docs/adr/` 根本不存在。新人(以及 AI)读代码时,无法回答"当初为什么这么设计",只能靠猜,于是每次改动都可能推翻上一次的隐含决策。

## 决策

采用 **ADR(Architecture Decision Record,架构决策记录)**。每做一个有长期影响的技术决策,就在 `docs/adr/` 下加一个编号 Markdown 文件,记录:背景、决策、后果。

- 文件名:`NNNN-简短标题.md`,编号递增。
- 已接受的决策不删改;若被推翻,新增一条 ADR 标注"取代 NNNN",保留历史。
- 格式保持极简:背景 / 决策 / 后果 三段。

## 后果

- 好处:任何人(答辩评委、未来的你、AI 助手)都能顺着 ADR 理解"为什么",不必逆向猜测。工程技能能读到这些决策,不会重复推翻。
- 代价:每个重要决策要多花几分钟写一页。这是值得的。
