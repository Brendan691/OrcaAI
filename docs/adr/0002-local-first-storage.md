# 2. 本地优先的存储架构(SQLite + 本地文件夹)

- 状态:已接受
- 日期:2026-07-27

## 背景

原设计参照重型多服务架构:元数据用 PostgreSQL、文件用 MinIO、全文检索用 Meilisearch、联网搜索用 SearXNG,靠 `docker-compose` 编排。但:

- 开发机没有 Docker,磁盘余量紧张(装齐镜像约 5GB)。
- `main.py` 启动即 `await init_db()` 连 Postgres,没有 Postgres 就**根本起不来**——与 README 宣称的"三步跑起来"直接矛盾。
- 这是个单人开发、需要本地演示和答辩的项目,不是高并发生产系统。

一个跑不起来的七服务架构,比一个一键就跑的精简单体更"毛坯"。

## 决策

**存储层做成可切换的抽象,默认走本地零依赖实现。**

| 关注点 | 本地默认(开发/演示) | 生产可选(compose 存档) |
|--------|--------------------|----------------------|
| 元数据 | SQLite(`aiosqlite`) | PostgreSQL |
| 文件 | 本地文件夹 | MinIO / S3 |
| 全文检索 | SQLite / Chroma 内建 | Meilisearch |
| 向量 | Chroma(本地持久化) | Chroma(同) |

- 通过环境变量切换实现,业务代码只依赖抽象接口,不依赖具体后端。
- `docker-compose.yml` 原样保留,写进《生产部署》文档,作为"可扩容"的证据。

## 后果

- 好处:`bash run.sh` 秒起,零外部服务(除 LLM API);磁盘占用从 ~5GB 降到 ~600MB;答辩话术成立——"本地零依赖开发,生产一键 compose 扩容"。
- 好处:存储选型对外不可见,不影响功能完整度。SQLite 是 iOS/Android/Chrome 内部在用的数据库,单机知识库正是它的主场。
- 代价:需要为存储层写抽象接口,并维护两套适配器。这是"两个适配器 = 真实的 seam"的正当投入。
- 边界:SQLite 单写并发有限;当真实多用户上线,按上表切 Postgres,接口不变。
